# GEL / FLOW — CRM производства гелей

Рабочий серверный проект с русским веб-интерфейсом: Django 5.2, Django REST Framework, PostgreSQL, Celery и Redis. Клиенты Windows, macOS, Android и iPhone используют один сервер и одну базу. Локальный режим SQLite позволяет начать без установки PostgreSQL.

Это первая прикладная версия с ограничениями, перечисленными ниже. Нативных APK/IPA/DMG/EXE здесь нет: установленная PWA использует тот же адаптивный интерфейс. Мессенджеры отмечены как модули подключения; действующих внешних переписок без реализации адаптеров и ключей API нет.

## Быстрый запуск на macOS / Linux

Нужен Python 3.12. Перейдите в папку проекта:

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.lock.txt
cp .env.example .env
python manage.py migrate
python manage.py seed_demo
python manage.py runserver 127.0.0.1:8000
```

Откройте <http://127.0.0.1:8000>. В `.env.example` установлен `DEBUG=true`: это режим разработки для локального HTTP. Без `DATABASE_URL` данные сохраняются в `db.sqlite3`, а не в памяти браузера.

## Быстрый запуск на Windows

Установите Python 3.12 с сайта python.org. В PowerShell внутри папки проекта:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.lock.txt
Copy-Item .env.example .env
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py seed_demo
.\.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8000
```

Активация виртуального окружения не требуется. Откройте <http://127.0.0.1:8000>. Для полного фонового режима на Windows используйте Docker Desktop: Celery worker на Windows напрямую не поддерживается.

## Полный запуск через Docker Desktop

Подходит для Windows, macOS и Linux. Нужны Docker Desktop либо Docker Engine с Compose v2. База, Redis, web, worker и единственный планировщик запускаются вместе.

1. Скопируйте `.env.example` в `.env`.
2. Замените `SECRET_KEY` и `POSTGRES_PASSWORD`. Для пароля PostgreSQL используйте длинное значение из букв, цифр, `-` и `_`: оно подставляется в URL соединения. Остальные специальные символы требуют URL-кодирования.
3. Для резервных копий создайте ключ Fernet и запишите его в `BACKUP_ENCRYPTION_KEY`. При пустом ключе копирование отключено, остальные разделы работают.

Генерация значений установленным Python:

```sh
python -c "import secrets; print(secrets.token_urlsafe(48))"
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Если локально зависимостей ещё нет, ключ можно сгенерировать в собранном образе:

```sh
docker compose build
docker compose run --rm --no-deps --entrypoint python web -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Запуск и, только для ознакомления, создание демо:

```sh
docker compose up --build -d
docker compose ps
docker compose exec web python manage.py seed_demo
```

Откройте <http://127.0.0.1:8000>. При `DEBUG=true` это локальная проверка, не открывайте её в Интернет. Миграции и сбор статических файлов выполняются web-контейнером автоматически; демо автоматически **не** создаётся. Worker и beat ожидают готовности web. Образ содержит PostgreSQL client 15, совместимый с сервером `postgres:15-bookworm` в Compose.

Обычная остановка сохраняет данные:

```sh
docker compose down
```

Не добавляйте `-v`, если данные нужно сохранить. Именованные тома `postgres_data`, `redis_data` и `backups` хранят БД, очередь и архивы. Redis и PostgreSQL не публикуются на сетевых портах хоста. Web по умолчанию доступен только через `127.0.0.1:8000`.

## Рабочий сервер и первый администратор

Для реальной эксплуатации настройте домен и HTTPS через доверенный reverse proxy. До запуска задайте:

```dotenv
DEBUG=false
SECRET_KEY=<длинное случайное значение>
POSTGRES_PASSWORD=<длинный уникальный пароль>
ALLOWED_HOSTS=crm.example.ru,localhost,127.0.0.1
CSRF_TRUSTED_ORIGINS=https://crm.example.ru
BACKUP_ENCRYPTION_KEY=<ключ Fernet>
BACKUP_RETENTION=5
```

Если reverse proxy работает в контейнере, подключите его к сети Compose и направьте запросы к `web:8000`; порт хоста можно оставить привязанным к loopback. Proxy должен сохранять `Host`, завершать TLS и передавать исходный HTTPS корректно. Настройки доверия к forwarded-заголовкам проверяйте под вашу схему: не принимайте произвольные заголовки от внешнего клиента. Cookie сессии и CSRF при `DEBUG=false` имеют признак Secure и требуют HTTPS.

Создайте владельца без демонстрационных пользователей:

```sh
docker compose exec web python manage.py create_admin --username owner
```

Введите пароль в скрытом интерактивном запросе. Email не нужен. Команда назначает прикладную роль `superadmin`: флаг Django `is_superuser` сам по себе не заменяет её. Затем входите как `owner` и создавайте сотрудников в разделе «Сотрудники». Для автоматизации команда также принимает пароль из переменной `CRM_ADMIN_PASSWORD`; передавайте её через механизм секретов среды, а не аргументом командной строки. Пароли хешируются средствами Django; пароль не возвращается API.

Запускайте только один beat для одной базы. Миграции при обновлении сервера применяйте после копирования рабочей БД, согласованно с остановкой старых workers. Образ собирается из `requirements.lock.txt`; `requirements.txt` задаёт диапазоны для осознанного обновления зависимостей. Перед реальным запуском проверьте права всех ролей, восстановление копии, импорт собственной выгрузки 1С и бизнес-правила на тестовой базе.

## Компьютеры и телефоны

Веб-версия работает в современном Chrome, Edge, Safari или Firefox на Windows и macOS. На Android откройте адрес сервера в Chrome и выберите «Установить приложение»; на iPhone — Safari → «Поделиться» → «На экран Домой». Для PWA необходим HTTPS; localhost — исключение только на том же устройстве. Интерфейс адаптируется к узкому экрану. Данные хранятся на сервере, офлайн-редактирования и разрешения конфликтов нет.

Для краткой проверки с телефона в одной доверенной сети можно запустить Django на `0.0.0.0:8000`, добавить IP компьютера в `ALLOWED_HOSTS`, а `http://<IP>:8000` — в `CSRF_TRUSTED_ORIGINS`, оставить `DEBUG=true` и разрешить порт в локальном firewall. В Compose дополнительно задайте `BIND_HOST=0.0.0.0`. Это открывает тестовый HTTP в локальной сети, а не создаёт защищённую рабочую установку. Для сотрудников используйте постоянный HTTPS-адрес. Все устройства должны обращаться к одному серверу: копирование SQLite на каждый компьютер не обеспечивает синхронизацию.

## Как работает производство

Стандартный заказ списывает готовый товар из каталога при запуске и проходит **комплектацию → отправку**. Если готового товара недостаточно, запуск отклоняется; выпуск партии оформляется индивидуальным заказом по рецептуре.

Индивидуальный заказ ссылается на отдельную рецептуру. Количество компонента рецептуры — расход на **одну единицу заказа**, в единице измерения выбранного материала. При запуске сервер умножает расход на количество заказа и атомарно списывает основу, пигменты, баночки и упаковку. Недостаток хотя бы одного компонента откатывает весь запуск. Готовый гель может быть отдельным складским материалом и входить в рецептуру.

Цепочка: **колеровка → розлив → маркировка → комплектация → отправка**. Следующий отдел получает задание после завершения предыдущего. Сотрудник принимает его на себя; завершение требует записи результата контроля качества. Возврат с обязательной причиной оставляет текущий этап на доработке и уведомляет администратора. После комплектации заказ готов, после отправки — отправлен. Повторный запуск и пропуск непереданного этапа запрещены на сервере.

Это списание при запуске, а не полноценная модель резервов, серий, партий и сроков годности. Отмена запущенного производства с автоматическим возвратом материалов не реализована; расход и корректировки должны отражаться отдельными складскими операциями с основанием.

## Клиенты, обращения, финансы и аудит

Телефон нормализуется: российские `8 (999)…`, `+7 (999)…` и десятизначный номер приводятся к одному значению. Телефон уникален; непустой email уникален без учёта регистра. Для создания нужен телефон или email. Новый клиент без менеджера попадает в общую очередь. Только администратор назначает либо вручную передаёт клиента; история сообщений сохраняется. Обычный менеджер работает с закреплёнными клиентами.

Встроенная переписка хранит сообщения CRM. Она не отправляет их в Telegram/WhatsApp/MAX/Instagram: активные внешние каналы требуют адаптера. Демо-сообщения с названиями каналов служат примерами, а не свидетельством установленной связи.

Оплаты, частичные возвраты и расходы хранятся отдельными записями. Возврат не может превысить полученные средства, оплата — остаток долга. Остаток долга учитывает возвраты. Это управленческий журнал в одной валюте (рубли), без фискальных чеков, банковского обмена и полноценной бухгалтерии.

Изменения через API и моделей отражаются в аудите с сотрудником и временем. Складские движения и импорт цен/остатков имеют отдельную историю. Журнал находится в той же базе; это не внешний неизменяемый журнал и не защита от администратора самой БД.

## Импорт каталога из Excel и 1С

Поддерживаются **XLSX, CSV и XML/CommerceML**. Старый Excel `.xls` не поддерживается. Сначала загрузите файл, проверьте предпросмотр и сопоставьте артикул, наименование, цену и остаток; затем явно примените. Предел: 5 МБ, 10 000 товаров и 64 столбца.

Артикул — ключ товара. Существующий артикул обновляет товар; дубли артикула внутри файла блокируют применение. Новому товару нужно название. Пустые/несопоставленные цена и остаток сохраняют прежнее значение; явный `0` означает ноль. Импорт применяется целиком или откатывается. История хранит старые/новые цены и остатки. Поля рецептуры отсутствуют в схеме импорта: ссылка на неё и её состав не затираются.

CSV понимает UTF-8/BOM и Windows-1251. XML обрабатывает товары/предложения CommerceML; DTD и внешние сущности запрещены. Поддержка CommerceML ограничена плоским каталогом и предложениями, сведёнными к одному артикулу и остатку: нет постоянного HTTP-обмена с 1С, характеристик, нескольких типов цен и полноценной многоскладской модели. Проверьте конкретную выгрузку вашей конфигурации 1С. Пример CSV:

```csv
Артикул;Наименование;Цена;Количество
GEL-NEW-15;Гель New Shade 15 мл;650,00;100
```

## Уведомления и фоновые задачи

Уведомления сохраняются в CRM: менеджеру — о сообщениях и назначениях, отделу — о передаче задания, администраторам — о низких остатках, доработках, задержках и ошибках копирования. Это внутренние уведомления, без системного push/SMS/email. Периодическая задача раз в минуту проверяет копии и задания без движения больше 24 часов; повторное предупреждение по заданию ограничено интервалом 12 часов.

Полный фоновый режим требует Redis + Celery worker + один Celery beat. Они уже есть в Compose. Один `runserver` не запускает планировщик. Для ручной локальной проверки можно отдельно поднять Redis и процессы с `celery -A config.celery worker --concurrency=1` и `celery -A config.celery beat`; укажите доступный `REDIS_URL` в `.env`. На Windows используйте Compose.

## Резервные копии и восстановление

Ключ `BACKUP_ENCRYPTION_KEY` — Fernet; архивы `.gelbackup` шифруются и проверяются по SHA-256. Они находятся вне web-статики, в `private_backups` либо в `BACKUP_DIR`. По умолчанию сохраняются 5 успешных копий (минимум 2); старые файлы удаляются по политике хранения, записи об этом остаются. В Compose web и worker используют один том `backups`.

Планировщик отсчитывает **12 часов после завершения последней успешной копии**, включая ручную. Ошибка не переносит этот срок. Если успешной копии ещё нет, при настроенном ключе планировщик ставит первую в очередь. Кнопка создания ставит фоновую задачу; результат виден после обработки worker. Конкурирующие операции защищены файловой блокировкой и advisory lock PostgreSQL. Максимальный дамп — 512 МиБ; упаковка и шифрование требуют дополнительной оперативной памяти. Для больших баз нужен отдельный потоковый сервис копирования.

Восстановление доступно только главному администратору: нужны его текущий пароль и фраза `ВОССТАНОВИТЬ`. До замены проверяются ключ, внешняя и внутренняя контрольные суммы, структура, движок и целостность дампа. Перед заменой создаётся защитная копия текущей базы. Во время восстановления обычные запросы записи блокируются; сессии завершаются, нужно войти снова. PostgreSQL восстанавливается одной транзакцией. Архив SQLite нельзя восстановить в PostgreSQL и наоборот. Восстановление выполняйте в согласованное окно обслуживания.

Храните копию ключа **отдельно от архивов**; без него архивы не расшифровать. Том на том же компьютере не защищает от потери диска: отдельно организуйте перенос шифрованных архивов и конфигурации на независимый носитель. Такой перенос и внешнее хранение здесь не автоматизированы. Резервируется база; исходный код, `.env`, сертификаты и внешние медиа требуют собственной копии. Фото в этой версии представлены URL, а не загруженными файлами.

При переносе архивов на другой сервер понадобятся также соответствующие записи `BackupRecord` из базы: интерфейс не импортирует произвольный архив с диска. Ключ нельзя менять без сохранения старого и плана повторного шифрования. Регулярно проверяйте восстановление на отдельной тестовой установке.

## Проверка и обслуживание

```sh
python manage.py check
python manage.py makemigrations --check --dry-run
python -m pytest
```

Тесты используют отдельную базу и не заменяют приёмку бизнес-процессов. В Docker:

```sh
docker compose exec web python -m pytest
docker compose logs --tail=100 web worker beat
docker compose exec web python manage.py check --deploy
```

`check --deploy` оценивает текущую конфигурацию: замечания о HTTPS/HSTS нужно решать вместе с reverse proxy, а не включать вслепую. Сборка и запуск Compose требуют работающего Docker daemon; наличие файлов Compose не является подтверждением проверенного контейнерного развёртывания.
